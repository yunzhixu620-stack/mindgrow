# MindGrow 生产环境测评集（2026-07-20）

## 1. 测评结论

本轮在登录后的生产环境直接执行 60 个案例，覆盖知识碎片、会议助手、文章解析各 20 个案例。结论不是“都能调用模型”，而是：

- 会议助手已经接近可用产品，严格通过 17/20，长会议中的精确数字保留仍需加强。
- 文章知识库是“已入库问答强、首次解析弱”。已有论文上的问答、比较、追问、拒答与 Audio Overview 基本可用；中文正文首次解析会退化为通用安全标签。
- 知识碎片的短文本与普通长文本整理可用，但生产版本中的网址输入并未真正读取网页，无效网址也没有拒绝，属于 P0。已在本地代码修正为“先抓取、后整理、失败即拒绝”，等待部署后复测。
- 整体建议定位为受控 Beta，不建议在修复网址入库和中文解析前承诺“任意网页/PDF 均可可靠建库”。

测试环境：`https://yunzhixu620-stack.github.io/mindgrow/`，登录云端工作区；生产 API 版本 10.2.9。延迟为浏览器端从提交到结果稳定出现的观测值。

## 2. 评分口径

| 维度 | 定义 |
|---|---|
| 关键事实召回 | 预设的人名、时间、数字、结论、否定条件是否进入结果 |
| 忠实度 | 是否只使用输入/知识库证据，是否混淆实体、时间与已否决信息 |
| 引用可核验性 | 结论能否回到正确原文、页码或来源，引用数量是否适度 |
| 拒答与边界 | 无证据、不可读链接、内网地址、表格列边界丢失时是否拒绝猜测 |
| 产品实用性 | 输出是否结论靠前、层次清楚、可继续追问、可保存和复用 |
| 响应体验 | 首次反馈是否及时、总等待是否可接受、长任务是否有明确状态 |

判定规则：通过 = 关键事实齐全且无实质错误；部分通过 = 主结论正确但有关键遗漏或交互缺陷；失败 = 未完成核心任务、产生无依据事实，或应拒绝而未拒绝。

## 5. 知识碎片应采用的三条产品链路

### 短文本

1. 识别为事实、观点、待办或问题。
2. 原文事实最多生成 3–8 个节点。
3. 扩展内容放到单独的“AI 建议扩展”层，默认折叠，并显示“非原文”。
4. 用户确认后才保存扩展节点。

### 长文本

1. 先给结论、实体/数字/否定条件清单，再生成 2–3 层导图。
2. 原文节点默认展示；扩展节点默认折叠。
3. 每个事实节点保存 `source_chunk_id`、原文短句、段落/页码和有效时间。
4. 对负责人、日期、版本、百分比与“未批准/已作废”做确定性校验，校验失败则不保存。

### 链接

1. 后端先做 URL 规范化、DNS/内网校验、重定向限制、状态码与内容类型校验。
2. 抓取成功后展示最终 URL、正文预览和来源；再把实际正文交给结构化模型。
3. 404、超时、受限页面、正文过短或内网地址直接返回可理解的拒绝原因。
4. 永远不要把裸 URL 当正文交给模型，也不要基于域名和路径猜测页面内容。

本轮已在本地实现第 1–4 条的基础版本，并给链接结果附加来源；同时在导图保存期间禁用输入，消除快速连续提交导致的待保存结果覆盖。

## 6. GraphRAG 为什么会定位不准

GraphRAG 不是“把向量检索换成图”就会自动更准。定位错误通常发生在六层：

1. **入口实体错**：别名、同名人、缩写和中英文实体被映射到错误节点。
2. **关系扩展过宽**：高连接度中心节点把大量相关但不回答问题的邻域带进来。
3. **关系没有状态**：历史版本、已作废决议、风险、假设和事实共用同一种边。
4. **查询模式选错**：具体实体问题却走全局社区摘要，或全局主题问题只走局部邻域。
5. **重排只看语义相似**：没有计算路径、实体类型、时间和来源一致性。
6. **图谱替代了原文**：图用于导航，但最终结论没有回到文本块/页码验证。

微软官方 GraphRAG 本身就区分 Local、Global、DRIFT 与 Basic Search：Local 面向具体实体，Global 面向全库主题，DRIFT 用社区信息扩展局部问题，Basic 保留普通向量检索作为基线与适用路径。[Query Engine](https://microsoft.github.io/graphrag/query/overview/) 官方索引也同时保存实体、关系、社区、原始 text units 和文档引用，而不是只保存一张抽象图。[Index outputs](https://microsoft.github.io/graphrag/index/outputs/) 官方还明确建议针对自己的数据做 prompt tuning，而不是直接沿用默认实体/关系抽取提示词。[Prompt tuning](https://microsoft.github.io/graphrag/prompt_tuning/overview/)

### 建议的定位链路

`查询分类 → 多路召回 → 实体消歧 → 受约束图扩展 → 路径/证据重排 → 原文核验 → 回答或拒答`

具体做法：

1. **查询路由**：精确名词/编号/表格值走 Basic + 元数据过滤；具体实体关系走 Local；跨主题、多跳问题走 DRIFT；全库概览才走 Global。
2. **多路入口**：实体别名精确匹配、BM25 文本块、向量实体召回并行；取并集，不让单一路径决定入口。
3. **强制消歧**：候选节点同时展示实体类型、来源文档、版本、时间和上下文；第一、第二候选分差过小时向用户反问，不自动选。
4. **受约束扩图**：默认最多两跳；按问题类型配置关系白名单；高连接度节点降权；历史/已作废/疑似关系单独标记；每条边必须有 `text_unit_id`。
5. **混合重排**：建议初始权重为实体锚点 28%、文本向量 24%、BM25 18%、路径匹配 14%、元数据 10%、时效 6%，再对冲突、过期和高连接度路径扣分。这组权重是 MindGrow 的初始实验建议，不是微软官方固定参数。
6. **证据闸门**：图只负责找候选；每个可验证句必须由原始文本块支持。没有原文、表格列边界或来源冲突时拒答。
7. **控制引用预算**：简单事实默认 2–5 条，高复杂多跳问题最多 8 条；其余证据折叠。A11/A17 的 22–24 条说明当前邻域扩展和引用预算过宽。

官方数据流是“文档切块 → 抽实体/关系/claims → 社区检测 → 社区报告 → 嵌入”，并保留原始文本块用于查询。[Indexing architecture](https://microsoft.github.io/graphrag/index/architecture/) 其配置也开放 `top_k_entities`、`top_k_relationships`、text/community 比例和上下文预算，正适合对定位误差做约束。[Configuration](https://microsoft.github.io/graphrag/config/yaml/)

### GraphRAG 专项验收指标

| 层级 | 指标 | 建议门槛 |
|---|---|---:|
| 实体 | Entity Hit@5、同名消歧准确率 | ≥ 95%、≥ 95% |
| 路径 | Gold Path Recall@10、无关边比例 | ≥ 90%、≤ 20% |
| 证据 | Citation Precision、Citation Recall | ≥ 95%、≥ 90% |
| 回答 | 关键事实召回、无依据事实率 | ≥ 90%、≤ 2% |

| 体验 | 简单问答 P95、复杂问答 P95 | ≤ 10 秒、≤ 25 秒 |
